# TMS 교환·반품 시스템 설계 플랜 (2026-08-25)

> 사장님 요구: 판매 상세에 「교환」 버튼. 단순 SKU 교체가 아니라 **수거·시리얼 무결성·반품창고·아임웹 실시간 연동**까지.
> 이 문서 = 전수 조사(교환/반품 흐름·수거 패턴·아임웹 API·창고 zone) 종합 + 단계 구현 플랜. **승인 후 착수.**

---

## 0. 한 줄 요약
교환 = **[신제품 OUT] + [구제품 IN(회수→반품창고)]** 두 흐름의 결합. 구 시리얼은 회수 실물에 그대로 남겨 **반품창고**로, 신제품은 **새 시리얼**로. 차액은 명시 회계. 아임웹은 **재고 복구·인바운드는 되지만 주문 취소/반품 아웃바운드는 미검증(실측 필요)**.

---

## 1. 현황 (조사 결과)

### 있는 것 (재사용 자산)
- **판매 수정 엔진** `rebuild_sale`(`api/sales/[id]/route.ts:530-828`): 시리얼 회수/재배정·재고 복원/차감·금액 재계산·미수금까지 이미 수행. **교환 백엔드의 90%.**
- **상태머신 SSOT 패턴** `lib/repair/transitions.ts`(맵+라벨+색+액션+수거방식 분기).
- **알림 인프라** `lib/notification/make-webhook.ts`(알림톡+사장님푸시+토글+웹훅분기) — 템플릿만 추가하면 됨.
- **공용 캘린더** `lib/schedule/use-schedule-events.ts`(방문수거 `pickup` kind 이미 존재) — 반품수거 kind 추가 쉬움.
- **시리얼 zone 복원 패턴** `previous_zone` 저장/복원. **SerialStatus `'returned'` 이미 존재**(types.ts:60).
- **수거 방식 4종 모델**(복원수리): 문앞/카운터/직접전달/직접발송. `proceed_type` 문자열 + `pickup_date` + `inbound_at`.

### 없는 것 (신규 필요)
- 전용 「교환」/「반품처리」 기능 (반품·취소는 **전량 단위** 플래그만, 부분·수거 다단계 없음).
- **반품 도메인 데이터 모델**: orders/sales에 `returned_at`/`return_reason` 플래그뿐 — 반품수거→입고완료 다단계 상태(pickup_date/inbound_at/status)를 담을 컬럼/테이블 없음.
- **'return' warehouse_zone**: 현재 zone = `raw`(보관)/`ready`(준비)/`display`(디스). **반품창고 없음.** (DB CHECK 제약 없어 마이그레이션 불필요 — 타입+리터럴 8곳만 확장)
- 반품 전용 알림톡 템플릿(수거접수/수거완료/입고완료).

### 🚨 시리얼 무결성 (사장님 강조 — 설계 원칙)
- 반품된 실물엔 **판매 당시 시리얼이 그대로 각인**돼 있음 → 교환 신제품에 그 시리얼을 **절대 덮어쓰지 않는다.**
- 원칙: **구 시리얼 = 구 실물에 귀속 → status `returned` + zone `return`(반품창고)**. **신제품 = 자기 재고에서 새 시리얼 배정.** (rebuild_sale이 이미 이렇게 동작하나, 교환 전용 UI에선 "구 시리얼 회수"를 `product_id 변경 감지`로 강제해 미지정 고아를 원천 차단)

## 2. 🚨 아임웹 연동 현실 (실측 근거)

| 방향 | 대상 | 상태 |
|---|---|---|
| 아웃바운드 | 배송상태(place/invoice/send/complete) | ✅ 실측 완료(2026-08-23) |
| 아웃바운드 | 재고 delta(±qty) | ✅ 동작 중(`adjustImwebStockDelta`) |
| 아웃바운드 | **주문 취소/반품/교환(claim)** | ❌ **미검증** — 전용 함수·엔드포인트 코드/문서에 없음. `updateProdOrderStatus`(CANCEL)는 **데드코드**. 취소접수 `PATCH /orders`는 문서상 "🔜 예정"일 뿐 실측 0. |
| 인바운드 | 아임웹발 취소/환불(CANCEL/REFUND_REQUEST/REFUND) | ✅ sync가 읽어 TMS 반영 |

→ **현재 온라인 주문 취소는 TMS 상태만 바꾸고 "아임웹에서 수동 취소하세요" 안내**(`imwebManual`). 반품/교환 아웃바운드를 자동화하려면 **아임웹 개발자센터 문서 확인 + 실호출 실측이 선행**돼야 함(place/send 검증했던 방식과 동일).

### 반품창고 ↔ 아임웹 재고의 함정
현재 취소/반품은 아임웹 판매재고에 **무조건 +qty**. 반품품을 "반품창고(검수대기·재판매불가)"에 두는데 아임웹에 +하면 **불량품이 아임웹에서 판매 가능 재고로 잡힘.** → **반품 zone은 아임웹 +push 보류**, 검수 후 `ready`로 옮길 때 비로소 +push하는 분기 필요.

## 3. 설계: 교환 처리 흐름

### 3-A. 교환 = 두 흐름의 결합
```
[신제품 OUT]  A2-68FS 새 시리얼 배정 → 매장 전달 or 배송(송장) → 재고 −
[구제품 IN ]  A2-65FS 회수 → 반품창고(return zone, status returned) → 재고 +(반품버킷)
[차액]        68FS가 − 65FS가 → 추가징수 or 환불 (명시 cash_transaction)
```

### 3-B. 회수(IN) 방식 — 복원수리 4종 재사용 + 매장
| 원 판매 상태 | 회수 방식 | 처리 |
|---|---|---|
| 매장 직접 | **매장 반납** | 즉시 입고완료 → 반품창고 |
| 배송/전달됨 | **방문수거**(문앞/카운터/직접전달) | 반품수거접수 → 일정 등록 → 기사 수거 → 입고완료 |
| 배송/전달됨 | **고객 직접발송(택배)** | 반품 안내(주소/송장) → 도착 → 입고완료 |

각 단계에 상태(`return_requested → pickup_scheduled → inbound → done`)와 알림톡. 캘린더에 반품수거 표시.

### 3-C. 신제품 전달(OUT) 방식
- 매장 전달: 즉시 출고.
- 배송: 송장 생성(기존 송장 흐름 재사용) → 아임웹 주문이면 배송상태 연동(place/invoice/send는 실측됨).

## 4. 단계별 구현 플랜 (독립 배포 가능, 리스크 순)

### Phase 1 — 매장 직접 교환 (가장 단순, 즉시 가치) ⭐
- 판매 상세 「교환」 버튼 → 교환 모달: 뺄 품목(65FS) 선택 / 넣을 제품(68FS)·**새 시리얼** 선택 / 차액 자동표시(추가수령·환불 명시).
- 내부: `rebuild_sale` 재사용 + **구 시리얼 → `returned`+`return` zone**(회수 강제) + 차액 cash_transaction 1줄.
- 'return' warehouse_zone 도입(타입+리터럴 8곳, 마이그레이션 불필요) + 창고·재고 화면에 반품 버킷 표시 + **아임웹 +push 보류 분기**.
- 무결성 불변식 갱신: 현재고 = raw + (ready+display) in_stock. **return zone은 별도 카운트(반품재고), 판매가능 현재고·아임웹엔 미반영.**
- 검증: 무결성 SQL + 시리얼 audit + tsc/build/실구동.

### Phase 2 — 배송 교환 + 반품수거 흐름
- 반품 도메인 데이터 모델 신설(반품 상태·pickup_date·inbound_at·수거방식·사유). `lib/return/transitions.ts`(repair 패턴 복제).
- 반품수거접수 → 일정/대시보드 캘린더 연동(`use-schedule-events`에 `return_pickup` kind 추가) → 입고완료 시 반품창고 이동.
- 반품 전용 알림톡(수거접수/수거완료/입고완료) + 사장님 푸시.
- 신제품 OUT 배송(송장) 연동.
- **✅ 롯데 반품 수거접수 자동화(2026-08-27, 마이그137)**: 롯데 IS팀 회신 — `ustRtgSctCd:'02'`=반품(양식 출고와 동일), `orglInvNo`=원송장(선택), 취소 API 미지원(접수 후 취소는 ALPS 수동). 구현=`bookShipment`에 ustRtgSctCd·orgInvoiceNumber 옵션 additive + `/api/returns/[id]/pickup`(고객주소로 반품접수→송장 저장·상태 pickup_scheduled) + `/returns` 「롯데 반품 수거접수」 버튼(pickup_method='택배수거'). ⚠️정답=snper=마모루/acper=고객 그대로+02(과거 01+역방향 테스트가 '출고'로 오판). [[reference_lotte_alps_invoice]]

### Phase 3 — 아임웹 반품/교환 실시간 연동 (실측 선행)
- **먼저 실측**: 아임웹 개발자센터에서 취소/클레임 API 존재·경로·페이로드 확인 → `imweb_order_test.gs`식 실호출로 검증(place/send 검증했던 방식).
- 되면: TMS 반품/교환 → 아임웹 주문 취소/클레임 자동 접수. 안 되면: 현행처럼 "아임웹 수동 처리" 안내 유지(정직하게).
- 아임웹발 반품/환불 인바운드(REFUND_REQUEST) → TMS 반품 흐름 자동 생성 검토.

### Phase 4 — 폴리시
- 부분반품(item 단위)로 반품 로직 확장(현재 전량 단위).
- 반품 사유 통계·반품률 리포트.

## 5. 🙋 사장님 확인 필요 (착수 전 결정)

1. **반품재고 카운트**: 반품창고 재고를 "현재고"에 포함해 볼지, 아니면 판매가능 현재고와 **분리 표시**(반품 N자루 별도)할지? (권장: 분리 — 검수 전까진 판매재고 아님)
2. **반품품 재판매 경로**: 검수 후 `ready`로 옮기면 다시 판매가능+아임웹 +push. 반품품을 항상 검수 거치게 강제할지, 상태 좋으면 바로 준비로 넣을지?
3. **차액 결제수단**: 추가징수/환불을 어느 수단(현금/카드/이체)으로 기록할지 기본값.
4. **범위**: Phase 1(매장 직접 교환)부터 만들고 배포하며 넓힐지, 아니면 Phase 2(수거)까지 묶어서 한 번에 볼지.
5. **아임웹 아웃바운드**: Phase 3 실측을 지금 같이 진행할지(내가 테스트 요청문 작성 → 크롬확장/gs로 실호출), 나중에 별도로 할지.
