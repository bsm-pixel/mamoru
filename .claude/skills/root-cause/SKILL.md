# 근본원인 추적 (표면패치 금지)

> 왜 있나: "일단 이거 고치고 다음에 또 보자" 식 즉흥 패치로 여러 라운드 낭비한 이력.
> 규칙: 증상만 보고 고치지 말고 **가장 깊은 뿌리부터 모든 경로를 훑은 뒤 통합 수정.**

## Phase 1 — 전수 탐색 (병렬)
- 관련 흐름의 **모든 경로**를 훑는다: 데이터 소스 → 훅 → API/RPC → DB 컬럼. 호출처·타임존·캐시·합산 로직.
- 넓으면 **Explore 에이전트 병렬**로 경로 매핑(어느 파일:라인이 그 값을 쓰고 바꾸는지).
- 같은 값을 쓰는 곳을 **grep 전수**: 목록·상세·모바일·PDF·알림톡·크론까지.

## Phase 2 — 모순 검증
- **같은 버그 패턴이 다른 파일에도 있는지 grep**(한 곳만 고치면 재발). 있으면 같이 고치거나 왜 안 고치는지 명시.
- 변경이 다른 화면/경로에 영향 주는지 점검.

## Phase 3 — 데이터 기반 진단 (추측 금지)
- 데이터 이슈면 **읽기전용 SQL/진단화면으로 실데이터 확인** 후 결론. "~일 겁니다" 금지.
- 재고/시리얼이면 불변식 `stock_quantity = raw_stock + in_stock 시리얼` 로 어느 값이 틀렸는지 특정.
- ⚠️ 상태를 바꾸는 루프 **뒤에** 그 값으로 판정하지 말 것 — 판정 기준은 변경 **전에 캡처**(무결성 -1 버그 교훈).

## Phase 4 — 회귀 위험 + 기계 검증
- 위험도 0이 아니면 명시. `npx tsc --noEmit` + `npm run build`. 재고 건드렸으면 `git diff|grep stock_quantity|raw_stock`.

## Phase 5 — 통합 fix + 보정 + 재발방지
- 발견된 관련 이슈를 **한 커밋에 통합**(위험 분리 필요 시 별도 PR로 명확히).
- **과거 데이터 보정**은 읽기전용 진단 SQL → 사용자 확인 → 보정 SQL 순서로. (의도적 이상치 `reference_known_data_anomaly` 는 제외)
- 교훈을 memory(reference)로 기록해 재발 방지.

## 보고 형식 (원인 + 왜 + 방지)
1. **원인** — 어느 파일:라인의 무엇이 (한 문장)
2. **왜 발생** — 증상과 수치가 어떻게 그 원인에서 나오는지(추적)
3. **재발 방지** — 코드 수정(대칭성·순서 등)
4. **과거 보정** — 진단 SQL + 보정 SQL (사용자 실행)

## 금지
- 증상만 가리고 root 미추적 / grep 안 돌리고 한 곳만 수정 / "다 됐어?"에 깊이 검증 없이 "네"
